# Same-unit increase and full-reversal barrier

This is a review-only incremental patch based on local `a4a2e6fdbf4516c6c1ac7d524acc29740df6af35`, the implementation represented by `partial-release.patch`. Apply and reconcile the active-line removal, payment-guard and current #1377 pack foundations first. Neither patch enables a router or may be deployed without the effective-allocation reader and residual-restoration integration.

`increaseSaleLineQuantity(db, scope, input)` is internal and supports same-unit increases only. The caller must authorize counter capability/branch and hold a transaction until commit. It acquires the shared sale/payment lock, rejects unresolved attempts and independently rejects paid or partially settled sales; it fails closed for clinical, historical and inconsistent evidence. FEFO allocation supplies new lot prices; original retained price evidence stays immutable. Discounts and approval are cleared. A request key gives retry identity, and successful replay does not allocate again. Unit changes, immediate-add wiring and any router are not implemented.

Migration `20261106130000_pharmacy_line_increase_evidence` adds nullable `requestKey` to `pharmacy_allocation_price_evidence`. Initial snapshots retain null. Added allocations use the increase's request key; `ordinal` remains a line-wide increasing sequence, and rounding `remainder` restarts at zero for each capture group. The existing reader formula remains per allocation: `remainingUnits = originalUnits - SUM(releases.canonicalUnits)` and `remainingGross = floor((remainder + remainingUnits * priceNumerator) / denominator)`. Snapshot rows and request rows remain append-only. Deferred checks require newly captured evidence and its request to belong to the same transaction; request and sale guards remain in force. Historical rows without snapshots fail edits closed. Retained historical cost handling and discount reapproval still require integrated review.

Migration `20261106140000_pharmacy_release_reversal_guard` serializes a full reversal on the scoped sale lock and rejects it when any partial release exists for the original movement. It does not implement residual restoration. If reversal wins first, the partial-release guard refuses the release; if release wins first, the full reversal refuses. This prevents the observed 20-unit full reversal from restoring an already-released 10 units. The existing exact-reversal trigger still rejects a linked 10-unit residual reversal of the 20-unit original. Void/removal must be integrated with the reader owner's linked, retry-safe residual-restoration design; until then, those paths fail closed after partial release. Do not enable editing or claim final restoration works.

Verified with fresh migrations on a disposable PostgreSQL clone containing the existing payment guard and active-line migration, using a NOSUPERUSER/NOBYPASSRLS runtime role. Prisma schema validation, typecheck, changed-file lint and 66 focused tests passed. These include mixed-price FEFO increases, repeat/retry behavior, two bills competing for last stock, discount clearing, cross-tenant/branch and stock denial, preparation-versus-edit in both orders, and full reversal-versus-release in both orders. These tests do not cover a working residual restoration, integrated pack binding, UI or all reader paths. Full integration and their associated race tests remain required.
