# Partial release integration artifact

This is a review artifact, not an enabled feature. The patch is based on #1367 at `da86acd8f45ac8703e1cf845f6f3128007ab80c0`; it also requires the shared active-line removal foundation and existing payment-attempt guard. It must be integrated with current #1377 pack binding and all effective-allocation readers before any caller or route is enabled. Do not deploy it independently. No payment feature changes are included.

The immutable table `pharmacy_allocation_price_evidence` stores one row per allocation, keyed by `(organizationId, allocationId)`: `branchId`, `ordinal`, `originalUnits`, `priceNumerator`, `denominator`, `remainder`, `grossMinor`. Evidence is captured only during initial allocation. Historical allocations without a snapshot cannot be edited; legacy unedited allocations remain readable under existing rules. Additional allocation snapshots for quantity increases are not implemented.

The append-only table `pharmacy_allocation_partial_releases` stores `id`, `organizationId`, `branchId`, `allocationId`, `stockMovementId`, `requestKey`, `idempotencyKey`, `actorId`, `canonicalUnits`, `grossMinor`, `createdAt`. Every row links an adjustment movement and a scoped `pharmacy_sale_line_edit_requests` row. It is not a full reversal and must not use `reversesMovementId`. The request table contains the scoped sale/line/actor, request idempotency key and from/to quantity.

For an allocation with snapshot and release rows, `remainingUnits = originalUnits - SUM(releases.canonicalUnits)` and `remainingGrossMinor = floor((remainder + remainingUnits * priceNumerator) / denominator)`. Original allocation, snapshot and release rows remain immutable history. Order by snapshot `ordinal`; removal, void, returns, receipt, finance and batch safety must consider only effective remaining units, avoid reversing already released movements, and retain historical evidence. Any missing or inconsistent snapshot fails edits closed. Pack bindings and mismatch checks must use the same sale lock and effective allocation/active-line state; do not rebind evidence to another line silently.

`reduceSaleLineQuantity(db, scope, input)` in `src/lib/pharmacy/edit-sale-line-quantity.ts` owns neither authorization nor transaction: callers must authenticate, check counter capability and branch assignment, and hold the transaction through commit. It is intentionally not exposed by a router. It supports only same-unit reductions on unpaid open bills, fails closed for restricted, controlled, Rx or high-alert lines, clinical history, returns, missing price evidence and physical splits requiring a pack break. It clears discount and approval fields. It does not implement increases, unit changes, immediate add, scan integration or UI. SQL constraints guard sale lock/payment uncertainty, tenders, cumulative units, movement scope/arrangement, money, release order, request linkage and final line/discount consistency. Historical controlled register and clinical evidence require separate integration before expanding eligibility.

Tested against a disposable PostgreSQL clone that already contained the existing payment guard and active-line removal migration, with `phase2_runtime` NOSUPERUSER/NOBYPASSRLS; role grants on the three new tables were applied in the test clone. Fresh migration application, Prisma validation, typecheck, lint and 52 focused tests passed. Tests cover competing reductions, request retries and conflicts, tenant/branch denial, mixed-price release order, discount clearing, over-release rollback, partially paid and restricted refusal, and both preparation-versus-edit lock orders. These tests do not establish safety of old allocation readers or pack binding. The SQL migration includes a deferred FK that Prisma cannot express; preserve it in hand integration.
