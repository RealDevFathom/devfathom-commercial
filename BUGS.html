Method: Deep static review of every router, REST endpoint, AI tool, auth/ABAC layer, and UI, plus live unauthenticated probes against the running dev server. Verdict — the security keystone is strong

Object-level authorization (IDOR/ABAC) has clearly been remediated and is applied consistently across tRPC, the REST /api/v1 surface, and all ~96 AI-assistant tools. No Critical and no High authorization defect was found — no cross-tenant IDOR, no privilege escalation, no ABAC bypass on layoff/resignation/role-change, no chat/DM privacy break, and the AI assistant cannot be coaxed into leaking finance or other users' data. Login hardening (timing-oracle defense, status allow-list, ~60s JWT revocation), invite tokens, and security headers are all sound.

The real defect concentration is in financial data integrity (caller-trusted invoice totals, mixed-currency summation, unbounded date windows) and functional correctness (kanban drag under filters, video-call attendance, chat edge cases), plus a cluster of information-disclosure / separation-of-duties gaps that are individually low-to-medium but worth closing.

FIN-01 — Invoice subtotal/tax/total are trusted from the client and never recomputed #

Module FinanceType Data integrityConfidence High
Module
Finance (finance.createInvoice tRPC + REST POST /api/v1/invoices)
Repro
Create an invoice with items:[{description:"Dev work",quantity:100,rate:150,amount:15000}] but subtotal:0, tax:0, total:0. The server stores total=0 while the line items represent $15,000 of work.
Expected vs Actual
Server should derive subtotal = Σ(items.amount) and total = subtotal + tax (or reject a mismatch). Actual: the inputs are written verbatim; there is no full invoice-edit mutation (only updateInvoiceStatus), so the wrong total is permanent and flows into totalPaid/totalOutstanding aggregates. Over REST you can even send total:-15000, which decrements the paid/outstanding sums.
Evidence Verified first-hand
src/server/routers/finance.ts:201-214 writes subtotal: input.subtotal, tax: input.tax, total: input.total with no cross-field .refine. REST is worse — src/app/api/v1/invoices/route.ts:43-48 uses bare z.number() for subtotal/tax/total/amount (no .positive()). Note the AI tool does it correctly (src/lib/ai/tools/finance.ts:482-490 recomputes with round2), proving the intended behavior.
Suggested fix
Recompute amount/subtotal/total server-side from items + tax in both tRPC and REST; ignore client-sent totals (or .refine they match). Add a full invoice-edit path.

FIN-02 — Every money aggregate sums across currencies (USD + PKR) into one number #

Module Finance/DashboardType Data integrityConfidence High
Module
Finance + Dashboard (summary, P&L, revenue chart, REST /finance/summary, AI finance tools)
Repro
Record June income of one USD transaction $5,000 and one PKR transaction Rs 280,000 (≈ $1,000). transaction.aggregate({_sum:{amount}}) returns 285000; the finance KPI and dashboard render it through a hardcoded $ → "$285,000" (true USD-equivalent ≈ $6,000 — overstated ~47×).
Expected vs Actual
Aggregates should group/convert by currency. Actual: no currency appears in any aggregate where/groupBy. PKR is a first-class currency reachable via the AI assistant and REST (createTransaction/createInvoice accept currency:'PKR' and render Rs …), making this latent-but-reachable, not theoretical.
Evidence Verified first-hand
src/server/routers/finance.ts:332-353 (summary) and :389-396 (P&L); src/server/routers/dashboard.ts:48-59, :200-214; src/app/api/v1/finance/summary/route.ts; src/lib/ai/tools/finance.ts:122-138. UI renders hardcoded $: finance-content.tsx:92, dashboard-content.tsx:932.
Suggested fix
groupBy:['currency'] and report per-currency, or filter aggregates to a single currency, or convert via an FX table before summing. Never _sum a mixed-currency column into one scalar.

FIN-03 — Dashboard revenue chart drops the last day of every month (+ month-overflow) #

Module Dashboard (getRevenueChart)Type Functional/DataConfidence High
Repro
A $5,000 income dated 2026-05-31 10:00 is excluded from the May bar.
Expected vs Actual
endOfMonth = new Date(y, m+1, 0) is the last day at 00:00:00.000, and the query filters date: { lte: endOfMonth }, so anything after midnight on the final day is cut. The P&L report uses …,0,23,59,59 and does include it, so the chart and the report disagree on every month's last day. Separately, date.setMonth(date.getMonth()-i) on today's day-of-month overflows on the 29th–31st (e.g. on May 31, stepping back to "Feb" rolls to Mar 3), duplicating/skipping a month.
Evidence
src/server/routers/dashboard.ts:190-215; contrast src/server/routers/finance.ts:386.
Suggested fix
Build months with new Date(y, m-i, 1) and set endOfMonth = new Date(y, m+1, 0, 23, 59, 59, 999).
