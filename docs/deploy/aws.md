# DevFathom on AWS

DevFathom's AWS environments replace the Azure ones (`infra/*.bicep`). Everything is
CloudFormation in `infra/aws/`, and the application image is the repository's own
`Dockerfile`, unchanged, plus one layer that adds Amazon's RDS CA bundle.

## Where it runs

|            |                                                                                                                       |
| ---------- | --------------------------------------------------------------------------------------------------------------------- |
| Account    | `892667864163`                                                                                                        |
| Region     | `ap-southeast-1` (Singapore)                                                                                          |
| Staging    | `staging.devfathom.com`, tenants at `<slug>.staging.devfathom.com`, platform console at `admin.staging.devfathom.com` |
| Production | not created yet: `environment.yaml` with `EnvironmentName=production`                                                 |

**Why Singapore.** The first choice was `me-central-1` (UAE), next to the old Azure UAE North
setup. That region has been impaired since physical damage to its data centres in March 2026,
and AWS has advised customers since 30 April 2026 to move to other regions. In this account,
every CodeBuild build there stayed queued, ECR refused pushes ("Image push is not available in
this region"), and ECS throttled cluster creation. Singapore is where the app ran on Vercel
(`vercel.json`, `sin1`), and every service works there.

## Stacks

| Stack                    | Template            | Region         | What it holds                                                                                                        |
| ------------------------ | ------------------- | -------------- | -------------------------------------------------------------------------------------------------------------------- |
| `devfathom-shared`       | `shared.yaml`       | ap-southeast-1 | ECR repository `devfathom-commercial`, build-source bucket, CodeBuild project `devfathom-image`                      |
| `devfathom-staging-dns`  | `dns.yaml`          | me-central-1*  | Route 53 zone for `staging.devfathom.com`                                                                            |
| `devfathom-staging`      | `environment.yaml`  | ap-southeast-1 | VPC, RDS PostgreSQL 16, secrets, uploads bucket, ECS cluster and services, load balancer, DNS records, jobs schedule |
| `devfathom-staging-cert` | `certificate.yaml`  | ap-southeast-1 | ACM certificate for `staging.devfathom.com` and `*.staging.devfathom.com`                                            |
| `devfathom-build`        | `build-remote.yaml` | us-east-1      | spare image build (not needed while Singapore CodeBuild works)                                                       |

\* Route 53 is global, so the zone serves every region. The stack happens to live in the
region that was tried first.

The parent zone, `devfathom.com`, is on Cloudflare. It delegates `staging` to the Route 53
zone with four NS records (the `NameServers` output of `devfathom-staging-dns`).

## Network and security

- **Subnets.** Two public subnets hold the load balancer and the Fargate tasks. The tasks have
  public addresses only for outbound traffic, because there is no NAT gateway; their security
  group admits only the load balancer on port 3000. Two private subnets hold the database,
  with no route to the internet.
- **Database.** RDS PostgreSQL 16, encrypted, `rds.force_ssl=1`, not publicly accessible,
  reachable only from the tasks' security group. Backups are kept for 7 days in staging and
  14 in production. Production is Multi-AZ. Deletion protection is on, and the stack keeps a
  final snapshot.
- **Database TLS.** The connection strings use `sslmode=verify-full&sslrootcert=/opt/devfathom/rds-global-bundle.pem`.
  - node-postgres (the app and the `bun prisma/*.ts` scripts) verifies the server against the bundle.
  - The Prisma schema engine (`prisma migrate deploy`) encrypts but does not verify, because
    it ignores `verify-full`. This is the same as on Azure.
- **Secrets.** All in Secrets Manager under `devfathom/<env>/…`. Each holds JSON `{"value": "…"}`.
  Every value is generated by Secrets Manager when the stack is created; none appears in a
  template, a parameter or the stack events.
  - Database: `database-master-password`, `database-app-password`, `database-admin-url`, `database-app-url`.
  - App: `auth-secret`, `platform-encryption-key`, `camera-credential-key`, `cron-secret`.
  - Initialization only: `seed-password`, `admin-password`, `platform-admin-password`.
- **Uploads.** A private, versioned bucket `devfathom-<env>-uploads-<account>`. The web task's
  role may get, put and delete objects in it, and nothing else. The app uses it once
  `StorageAdapter=s3` and the image has the S3 adapter (`src/lib/storage.ts`).

## Build an image

Images are tagged with the full commit sha, and tags are immutable.

1. Make a source archive of the commit: `git archive --format=zip -o <sha>.zip <sha>`.
2. Upload it to `s3://devfathom-build-892667864163-ap-southeast-1/source/<sha>.zip`.
3. Start CodeBuild project `devfathom-image` with source override
   `devfathom-build-892667864163-ap-southeast-1/source/<sha>.zip` and environment variable
   `IMAGE_TAG=<sha>`.
4. The build log ends with the image digest. Deploy by digest:
   `892667864163.dkr.ecr.ap-southeast-1.amazonaws.com/devfathom-commercial@sha256:…`.

The build takes about 5 minutes on the 15 GB compute type. That size is needed because the
Dockerfile's `tsc --noEmit` runs with an 8 GB heap.

## Deploy an image

1. Update stack `devfathom-staging` with the new `ImageUri`, keeping every other parameter.
   This registers new task-definition revisions. The web service then rolls, with the
   deployment circuit breaker set to roll back.
2. Run the migration task **before** the new web tasks need the new schema:
   - `aws ecs run-task --cluster devfathom-staging --launch-type FARGATE --task-definition devfathom-staging-migrate …`
   - Use the stack outputs `TaskSubnetIds` and `AppSecurityGroupId`, with public IP enabled.
   - Its default command is the migration-only path from `infra/environment.bicep`:
     `bun prisma/prepare-extensions.ts && bunx prisma migrate deploy && bun prisma/prepare-runtime-role.ts && bun prisma/sync-catalog.ts`.
   - The load balancer health check is `/api/ready`, which fails while migrations are
     pending, so a web task never takes traffic against an unmigrated database.
3. Watch the service until it is stable, then check `https://staging.devfathom.com/api/ready`.

**First deploy of a new environment.** Override the migration command to append
`&& bun prisma/seed.ts` (staging: demo data) or `&& bun prisma/bootstrap.ts`
(production: first administrators, no demo data). The first sign-ins are `admin@<base>`
and `platform-admin@<base>`. Their passwords are in Secrets Manager, in `admin-password` and
`platform-admin-password`.

**Rollback.** Update `ImageUri` back to the previous digest. Migrations only go forward, so
roll back only to an image whose schema expectations are still met.

## HTTPS and the jobs schedule

1. Once the Cloudflare delegation answers, create `certificate.yaml` (`DomainName`,
   `HostedZoneId`). It validates through the Route 53 zone.
2. Update the environment stack:
   - Set `CertificateArn`. Port 80 then redirects to 443, with TLS 1.2 minimum.
   - Set `EnableJobsSchedule=true`. Every 5 minutes a small Lambda function calls
     `POST https://<TenantHost>/api/platform/jobs/process` with `Authorization: Bearer <cron-secret>`,
     replacing `vercel.json`'s cron.

## Database access for people

There is none from the internet. For a one-off query, run a task in the cluster from the
migration task definition with a command override.

## Cost

Staging, on demand: roughly US$90–110 a month. The main items:

- the database (db.t4g.small, 20 GB gp3);
- one Fargate task (1 vCPU, 2 GB);
- the load balancer;
- public IPv4 addresses.

Builds cost cents.

## Not yet on AWS

- **Email** stays in `capture` mode, as on Azure: nothing is sent.
- **AI** (`AI_PROVIDER`) is `disabled`; Azure OpenAI was Azure-only.
- **Meetings:** the LiveKit server (`infra/meetings.bicep`) is not ported. Calls need `NEXT_PUBLIC_LIVEKIT_URL`.
- **Public URLs:** the metadata base URL and the plain-text email footer still name `dev-fathom-hub.vercel.app` until the production domain is final.
