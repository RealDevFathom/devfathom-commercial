# DevFathom on AWS

DevFathom runs on AWS. Everything is CloudFormation in `infra/aws/`, and the application image
is the repository's own `Dockerfile`, unchanged, plus one layer that adds Amazon's RDS CA bundle.

## Where it runs

|            |                                                                                                  |
| ---------- | ------------------------------------------------------------------------------------------------ |
| Account    | `<account-id>`                                                                                   |
| Region     | `ap-southeast-1` (Singapore)                                                                     |
| Staging    | `<staging-host>`, tenants at `<slug>.<staging-host>`, platform console at `admin.<staging-host>` |
| Production | not created yet: `environment.yaml` with `EnvironmentName=production`                            |

**Why Singapore.** The first choice was `me-central-1` (UAE). That region has been impaired
since physical damage to its data centres in March 2026, and AWS has advised customers since
30 April 2026 to move to other regions. In this account, every CodeBuild build there stayed
queued, ECR refused pushes ("Image push is not available in this region"), and ECS throttled
cluster creation. Singapore is where the app ran on Vercel
(`vercel.json`, `sin1`), and every service works there.

## Stacks

| Stack                    | Template           | Region         | What it holds                                                                                                        |
| ------------------------ | ------------------ | -------------- | -------------------------------------------------------------------------------------------------------------------- |
| `devfathom-shared`       | `shared.yaml`      | ap-southeast-1 | ECR repository `devfathom-commercial`, build-source bucket, CodeBuild project `devfathom-image`                      |
| `devfathom-staging-dns`  | `dns.yaml`         | me-central-1*  | Route 53 zone for `<staging-host>`                                                                                   |
| `devfathom-staging`      | `environment.yaml` | ap-southeast-1 | VPC, RDS PostgreSQL 16, secrets, uploads bucket, ECS cluster and services, load balancer, DNS records, jobs schedule |
| `devfathom-staging-cert` | `certificate.yaml` | ap-southeast-1 | ACM certificate for `<staging-host>` and `*.<staging-host>`                                                          |

\* Route 53 is global, so the zone serves every region. The stack happens to live in the
region that was tried first.

`build-remote.yaml` builds in a second region and pushes to the app region's repository, for a
region whose CodeBuild has no capacity. Singapore's has, so nothing uses it.

Left over from the me-central-1 attempt, both empty: `devfathom-build` in us-east-1 (it targets
the me-central-1 repository, which no longer exists) and `devfathom-staging` in me-central-1
(a failed create, `ROLLBACK_FAILED`, with termination protection on). Either can be deleted.

The parent zone is on Cloudflare. It delegates `staging` to the Route 53
zone with four NS records (the `NameServers` output of `devfathom-staging-dns`).

## Network and security

- **Subnets.** Two public subnets hold the load balancer and the Fargate tasks. The tasks have
  public addresses only for outbound traffic, because there is no NAT gateway; their security
  group admits only the load balancer on port 3000. Two private subnets hold the database,
  with no route to the internet.
- **Database.** RDS PostgreSQL 16, encrypted, `rds.force_ssl=1`, not publicly accessible,
  reachable only from the tasks' security group. Backups are kept for 7 days in staging and
  14 in production. Production is Multi-AZ. Deletion protection is on, and the stack keeps a
  final snapshot.
- **Database TLS.** The connection strings use `sslmode=verify-full&sslrootcert=/opt/devfathom/rds-global-bundle.pem`.
  - node-postgres (the app and the `bun prisma/*.ts` scripts) verifies the server against the bundle.
  - The Prisma schema engine (`prisma migrate deploy`) encrypts but does not verify, because
    it ignores `verify-full`.
- **Secrets.** All in Secrets Manager under `devfathom/<env>/…`. Each holds JSON `{"value": "…"}`.
  Every value is generated by Secrets Manager when the stack is created; none appears in a
  template, a parameter or the stack events.
  - Database: `database-master-password`, `database-app-password`, `database-admin-url`, `database-app-url`.
  - App: `auth-secret`, `platform-encryption-key`, `camera-credential-key`, `cron-secret`.
  - Initialization only: `seed-password`, `admin-password`, `platform-admin-password`. They
    reach the migration task only in `seed` or `bootstrap` mode (see below).
  - The database passwords and the two encryption keys are kept if the stack is deleted, as
    the database's final snapshot is: data encrypted under a lost key (MFA, SSO and camera
    credentials) could not be recovered. A new stack with the same `EnvironmentName` has to
    delete or rename those secrets first.
- **Uploads.** A private, versioned, TLS-only bucket `devfathom-<env>-uploads-<account>`. The
  web task's role may get, put and delete objects and list the bucket, and nothing else; the
  listing permission is what makes S3 answer 404, not 403, for a missing object. The app uses
  the bucket once `StorageAdapter=s3` (`src/lib/storage.ts`). An overwritten or deleted upload
  stays as an old version for 30 days, so a delete, a purge included, becomes permanent only
  after that window.
- **Plain HTTP.** Never served. Until `CertificateArn` is set, port 80 answers 503 with a short
  notice; once it is set, port 80 redirects to HTTPS (TLS 1.2 minimum). Meanwhile a listener
  rule that no request can match keeps the target group attached, because the load balancer
  health-checks only a target group that some rule uses.
- **Client addresses.** The web task sets `TRUSTED_PROXY_HOPS=1`: the load balancer appends the
  client's address to `X-Forwarded-For`, and rate limits read that last entry. Production
  refuses to start without one of `CLIENT_IP_HEADER`, `TRUSTED_PROXY_CIDRS` or
  `TRUSTED_PROXY_HOPS`.
- **Health checks.** The load balancer checks `/api/live`, which reads nothing, because ECS
  replaces the tasks that fail it: a check on the database would fail on every task at once
  during a failover or maintenance. `/api/ready` (half-applied migrations, schema drift on the
  generated client) is the deploy-time check below.

## Build an image

Images are tagged with the full commit sha, and tags are immutable.

1. Make a source archive of the commit: `git archive --format=zip -o <sha>.zip <sha>`.
2. Upload it to `s3://devfathom-build-<account-id>-ap-southeast-1/source/<sha>.zip`.
3. Start CodeBuild project `devfathom-image` with source override
   `devfathom-build-<account-id>-ap-southeast-1/source/<sha>.zip` and environment variable
   `IMAGE_TAG=<sha>`.
4. The build log ends with the image digest. Deploy by digest:
   `<account-id>.dkr.ecr.ap-southeast-1.amazonaws.com/devfathom-commercial@sha256:…`.
   - ECR keeps the 10 newest other images. Before deploying an image to production, also tag it
     `prod-<sha>` (or `release-<name>`); the lifecycle policy never expires those tags.
   - Logs are kept 7 days outside production; production keeps web and jobs 30 days, migrate 90.

The build takes about 5 minutes on the 15 GB compute type. That size is needed because the
Dockerfile's `tsc --noEmit` runs with an 8 GB heap.

## Deploy an image

Migrate first, then roll the web service. Nothing else enforces that order: `/api/ready`
fails for a migration that stopped part-way, but not for one that has not started.

1. Update the stack with `MigrateImageUri=<new image>`, keeping every other parameter. Only
   the migration task definition changes; the web service keeps its image.
2. Run the migration task and wait for exit code 0:
   - `aws ecs run-task --cluster devfathom-<env> --launch-type FARGATE --task-definition <MigrateTaskDefinitionArn output> …`
   - Use the stack outputs `TaskSubnetIds` and `AppSecurityGroupId`, with public IP enabled.
   - Its log is in `/devfathom/<env>/migrate`.
   - Its command is
     `bun prisma/prepare-extensions.ts && bunx prisma migrate deploy && bun prisma/prepare-runtime-role.ts && bun prisma/sync-catalog.ts`,
     followed by what `MigrationMode` selects. Staging runs `seed`: every
     release re-runs `prisma/seed.ts`, which creates the demo data once and refreshes the
     platform administrator's password. Production runs `migrate`.
3. Update the stack with `ImageUri=<new image>` and `MigrateImageUri` empty. The web service
   rolls; the deployment circuit breaker rolls back a task that will not start or fails
   `/api/live`.
4. Check `https://<TenantHost>/api/ready`: 200 with `{"status":"ok","schema":"current"}`.

**First deploy of a new environment.** Create the stack with `ImageUri` set, `DesiredCount=0`
and `MigrationMode=seed` (staging) or `bootstrap` (production, which creates the first
administrators and no demo data). Run the migration task, then update `DesiredCount=1`; in
production, also set `MigrationMode=migrate` again, because the bootstrap runs once.

The staging logins are kept outside git. Ask the CTO or Inky for them; never put them in docs, PRs or chat.

**Rollback.** Update `ImageUri` back to the previous digest. Migrations only go forward, so
roll back only to an image whose schema expectations are still met.

## HTTPS and the jobs schedule

1. Create `certificate.yaml` (`DomainName`, `HostedZoneId`). It validates through the Route 53
   zone, so the stack completes only once the Cloudflare delegation answers.
2. Update the environment stack:
   - Set `CertificateArn`. Port 80 then redirects to 443, with TLS 1.2 minimum.
   - Set `EnableJobsSchedule=true`. Every 5 minutes a small Lambda function calls
     `POST https://<TenantHost>/api/platform/jobs/process` with `Authorization: Bearer <cron-secret>`,
     replacing `vercel.json`'s cron.

A failed call is not retried; the next run is 5 minutes later, and overlapping runs are safe
(jobs are claimed with `SKIP LOCKED`). `maxDuration` is advisory outside Vercel, so a run
longer than the load balancer's 310 s idle timeout ends in a 504 for the caller while the
work itself continues.

## Database access for people

There is none from the internet. For a one-off query, run a task in the cluster from the
migration task definition with a command override.

## Cost

Staging, on demand: roughly US$90–110 a month. The main items:

- the database (db.t4g.micro, single-AZ outside production, 20 GB gp3, 1-day backups);
- one Fargate task (1 vCPU, 2 GB);
- the load balancer;
- public IPv4 addresses.

Builds cost cents.

## Not yet on AWS

- **Email** stays in `capture` mode: nothing is sent.
- **AI** is not rolled out yet.
  - The template's `AiProvider` defaults to empty, which means the environment default: `auto`
    (the routed chain: Anthropic, OpenAI, then Bedrock) in staging, and `disabled` in production.
  - Bedrock runs from `AiBedrockRegion` (default `ap-southeast-1`) on the global inference
    profiles.
  - The keys are read at runtime from existing Secrets Manager secrets through the web task role.
  - Variables, IAM and the rollout steps are in [AI providers](../ai-providers.md).
- **Meetings:** the LiveKit server is not deployed on AWS. Calls need `NEXT_PUBLIC_LIVEKIT_URL`.
- **Public URLs:** the metadata base URL and the plain-text email footer still name `dev-fathom-hub.vercel.app` until the production domain is final.

## Staging demo tenants

In `seed` mode the migration task runs `bun scripts/seed-staging-demo.ts`, which first refuses
unless `DEPLOY_ENV` is `staging` and both database URLs point at the stack's
`devfathom-staging` RDS endpoint in ap-southeast-1, then runs `prisma/seed.ts` and seeds the pharmacy tenant (`pharmacy-counter-e2e`) and restaurant
demo seat 1 (tax-inclusive, passwordless personas behind `DEMO_ACCESS_CODE`, secret
`demo-access-code`). The agency workspace and SuperAdmin come from `prisma/seed.ts`. The
pharmacy password is HMAC-derived from `seed-password`, so an operator writes the login sheet
without a database connection:

    SEED_PASSWORD=… PLATFORM_ADMIN_PASSWORD=… DEMO_ACCESS_CODE=… PLATFORM_BASE_DOMAIN=<staging-host> \
      STAGING_LOGINS_FILE=<path outside git> bun scripts/seed-staging-demo.ts --logins-only

The resulting login sheet stays outside git; the CTO or Inky hand it over.

## Staging checklist: Insights and app URLs

- Insights and other background work run only through `/api/platform/jobs/process`. On AWS that
  is the `platform-jobs` scheduler, which is created only when the stack parameter
  `EnableJobsSchedule=true` (default `false`). Staging must deploy with `EnableJobsSchedule=true`
  now that DNS and the certificate are live; also confirm the `cron-secret` secret is set.
- `AUTH_URL`, `NEXTAUTH_URL` and `NEXT_PUBLIC_APP_URL` are all `https://${TenantHost}`; keep
  `TenantHost=<staging-host>` for staging.
- `NEXT_PUBLIC_APP_URL` is inlined by `next build`. `Dockerfile` and `Dockerfile.aws` take it as
  a build argument: build staging images with
  `--build-arg NEXT_PUBLIC_APP_URL=https://<staging-host>` (production: its own host). CodeBuild: start the build with
  `--environment-variables-override name=NEXT_PUBLIC_APP_URL,value=https://<staging-host>`.
