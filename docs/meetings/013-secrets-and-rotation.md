# 013 — Secrets and rotation

Two secrets exist for Meetings staging:

| Key Vault secret | Consumed by | Purpose |
| --- | --- | --- |
| `livekit-api-key` | LiveKit server, application token signer | Identifies the key pair |
| `livekit-api-secret` | LiveKit server, application token signer | HMAC key for access tokens |

Vault: `df-mtg-stg-<suffix>-kv`, RBAC-authorised, purge protection on, 7-day soft
delete. Read by the VM's user-assigned managed identity, which holds **Key Vault
Secrets User** and nothing more — it can read secret values and cannot write,
delete, or list vault configuration.

## What is deliberately not done

- **Neither secret is a Bicep parameter**, `@secure()` or otherwise. A
  `@secure()` parameter is redacted in the portal but its value still passes
  through the deployment request, and deployment history is readable by any
  subscription reader. Not putting the value in the request is stronger than
  hiding it in one.
- **Neither secret is in `cloud-init`.** `customData` is readable from inside the
  VM and, on some configurations, from the instance metadata service. It contains
  `fetch-keys.sh` — instructions to go and get a secret — never a secret.
- **Neither secret is baked into an image.**
- **Neither secret is in this repository**, in `.env.example`, in a test fixture,
  or in a doc. The local development stack in
  [010-local-livekit.md](010-local-livekit.md) mints an entirely separate pair
  that never touches Azure.
- **No secret is generated by the template.** A template that generates a secret
  puts it in the deployment output or the vault via the deployment, which is the
  same leak wearing a hat.

## Seeding, once, after provisioning

The vault is created empty. The operator seeds it by hand. This is one command
each and it happens exactly once per environment.

```bash
VAULT=df-mtg-stg-<suffix>-kv

# Generate the pair. The livekit-server image is the authority on the format,
# and this runs locally — the values never reach a build log or a CI variable.
docker run --rm \
  livekit/livekit-server:v1.13.5@sha256:3497163e15c48fef6e7830c78716f9e9d5edc28abf7aa90b61c86e93bbc306b1 \
  generate-keys
# API Key:     API...
# API Secret:  ...

az keyvault secret set --vault-name "$VAULT" --name livekit-api-key    --value "API..." --output none
az keyvault secret set --vault-name "$VAULT" --name livekit-api-secret --value "..."    --output none
```

Notes:

- Pass `--output none`. Without it, `az keyvault secret set` prints the secret
  value to the terminal and into any shell transcript or CI log.
- Clear the shell history entry afterwards, or use `--file` with a file you
  delete. A secret in `~/.zsh_history` is a secret in a backup.
- The same pair must be given to the application so it can sign join tokens. That
  hand-off is the application workstream's concern; it reads from the same vault
  with its own identity, it does not receive a copy over chat.

## Boot-time retrieval

`/opt/livekit/fetch-keys.sh`, written by `cloud-init` at mode `0700`:

1. Requests an IMDS token for `https://vault.azure.net` scoped to the VM's
   user-assigned identity `client_id`.
2. Reads both secrets from the vault REST API (`api-version=7.4`).
3. Asserts both are non-empty and not the string `null` — a failed fetch must
   stop the unit, not write a broken key file and let LiveKit start with no
   authentication.
4. Writes `/opt/livekit/keys.yaml` under `umask 077`, then `chmod 600`.

It runs as `ExecStartPre` of the `livekit.service` unit, so it executes on **every
boot and every restart**, not once at provisioning. `curl` retries five times with
a five-second delay, because IMDS and the vault are both reachable slightly after
the network is, and a race at boot should resolve itself rather than page someone.

## Rotation

Rotation is: write a new value, restart the service. There is no redeploy and no
template change.

```bash
VAULT=df-mtg-stg-<suffix>-kv
RG=rg-devfathom-staging-uaenorth
VM=df-mtg-stg-<suffix>-vm

# 1. New pair
docker run --rm livekit/livekit-server:v1.13.5@sha256:3497163e15c48fef6e7830c78716f9e9d5edc28abf7aa90b61c86e93bbc306b1 generate-keys

# 2. New secret versions. Old versions stay in the vault for rollback.
az keyvault secret set --vault-name "$VAULT" --name livekit-api-key    --value "API..." --output none
az keyvault secret set --vault-name "$VAULT" --name livekit-api-secret --value "..."    --output none

# 3. Update the application's copy FIRST, then restart the SFU.

# 4. Drain check, then restart — see 015-staging-operations.md.
az vm run-command invoke --resource-group "$RG" --name "$VM" \
  --command-id RunShellScript \
  --scripts "systemctl restart livekit && sleep 5 && docker compose -f /opt/livekit/docker-compose.yml ps"
```

### Rotation is disruptive, and the ordering matters

LiveKit holds one key pair. When it restarts with a new one:

- Every token signed with the **old** secret stops validating. Participants
  already in a room keep their media path but cannot rejoin, and anyone opening a
  page with a pre-issued token gets rejected.
- Tokens signed with the **new** secret only validate after the restart
  completes.

There is no overlap window with a single key pair, so:

1. Write the new pair to the vault.
2. Update the application's signing configuration to the new pair.
3. **Wait for the SFU to be empty** — the drain check in
   [015-staging-operations.md](015-staging-operations.md) — then restart.

Rotating during an active meeting ends that meeting. Rotate inside the
maintenance window.

### Rollback

Every `az keyvault secret set` creates a new version; older versions remain
readable.

```bash
az keyvault secret list-versions --vault-name "$VAULT" --name livekit-api-secret \
  --query "[].{id:id, created:attributes.created, enabled:attributes.enabled}" -o table

# Restore by writing the previous value back as a new current version.
az keyvault secret set --vault-name "$VAULT" --name livekit-api-secret \
  --value "$(az keyvault secret show --id <previous-version-id> --query value -o tsv)" \
  --output none
```

`fetch-keys.sh` always reads the current version, so rollback is also "write, then
restart".

## Cadence and triggers

- **Scheduled:** every 90 days, in a maintenance window.
- **Immediate, out of cycle:** any suspicion of exposure — a secret pasted into a
  log, an issue, a screenshot, a chat, or a terminal someone else can scroll; an
  operator with vault access leaving; a VM disk snapshot leaving the subscription.
- **After incident response** that involved reading `/opt/livekit/keys.yaml`.

## If a secret is exposed

1. Rotate immediately. Do not wait for the window; an active-meeting outage is
   cheaper than a forged token.
2. Check Key Vault audit logs in Log Analytics for reads that were not the VM's
   identity:

   ```kusto
   AzureDiagnostics
   | where ResourceProvider == "MICROSOFT.KEYVAULT"
   | where OperationName == "SecretGet"
   | project TimeGenerated, identity_claim_appid_g, requestUri_s, ResultSignature
   ```

3. Record the exposure and the rotation in the incident log.

Forged tokens are the risk being managed here: the API secret is the HMAC key for
join tokens, so anyone holding it can mint a token for any room with any grants,
including rooms they were never invited to.

## Secret scanning before commit

Before every commit on this workstream:

```bash
git diff --cached | grep -nEi 'API[A-Za-z0-9]{10,}|api[_-]?secret|LIVEKIT_API|BEGIN [A-Z ]*PRIVATE KEY|[A-Za-z0-9+/]{40,}={0,2}'
```

Empty output is the pass condition. This is a coarse filter and it is meant to
be: a false positive costs ten seconds of reading, a false negative costs a
rotation and an incident report.
