# UX-03: Visual audit of the running screens

Owner: UX consultant · Issue: WHA-1601 · Build audited: `215568faf361ee49807c95fe69e00fa71b6565f2`
(tip of `codex/restaurant-release-20260911`, 2026-10-02) · Status: proposed, for board review

UX-AUDIT-01 (`01`) and UX-02 (`06`–`09`) were derived from code. This audit is derived from the
**running app**. It covers 20 screen states, each at three viewports (1024×768, 1366×768, 768×1024
portrait) in light and dark: **120 screenshots**. Each screenshot also has DOM metrics: interactive
elements under 44 px, ellipsis/clamp truncation, WCAG contrast of every text node against its real
background, light surfaces in dark mode, scroll containers with hidden height, and horizontal
overflow. Every finding below was checked against the screenshot. Every `file:line` was checked at
`215568fa`.

> File number: `06-` was requested in the brief. It sits next to the earlier
> `06-pharmacy-counter-flows-spec.md`. The two are unrelated; this one is the visual audit.

## 0. How to read this

- **Evidence root**: `paperclip-worktrees/devfathom/_evidence/ux-03/` (not committed).
  - `shots/<state>/<viewport>-<theme>.png`, e.g. `shots/pos-05-ticket-with-items/1024x768-light.png`
  - `metrics/<state>.json`: the raw numbers each finding quotes
  - `capture-log.txt`: all 20 states `ok`, 0 `FAIL` in the final runs
  - `capture-script/`: the lane script, Playwright spec and config, so anyone can reproduce
  - `logs/`: lane, seed, build and capture logs
- **Lane**: PG 16.15 on `127.0.0.1:55613`. Owner role is NOSUPERUSER NOBYPASSRLS CREATEROLE; runtime role is LOGIN NOSUPERUSER NOBYPASSRLS. Order of setup:
  1. prepare-extensions
  2. `migrate deploy` (110 migrations)
  3. seeds, as the runtime role: base, restaurant e2e, pharmacy counter e2e, pharmacy purchasing e2e
  4. `next build` (exit 0), then `next start`
  - Fixture changes, all in the disposable DB only:
    - One SUPER_ADMIN `platform_users` row for the console.
    - The procurement module enabled on the counter fixture. It had no effect, so receiving was captured with the PH-PUR receiver.
- **Severity**: **P0** stops a cashier, cook or pharmacist finishing the task on that device class. **P1** costs time or errors on every transaction, or fails WCAG AA on primary text. **P2** is polish or consistency.
- **Token to change**: the exact token or class, and the value to change it to. Ratios were measured on the rendered page; proposed values were computed against the same backgrounds.

## 8. Limits and what was not covered

- **Receiving line capture is not audited.** The script selected a PO, but the line grid didn't open in the capture (`ph-06` is the same as `ph-05`). Follow-up: drive the PO picker the way `tests/e2e/pharmacy-purchasing.spec.ts` does, and re-shoot.
- **Checkout tender pad and split bills, refund, operator switch, delivery channel, offline banners** were not captured. Offline banners are covered in copy by `08`.
- **Tap-target metric** counts the element box, not the hit area of an enclosing `<label>`. Checkbox and radio hits were checked against the screenshot (POS-8).
- **Dev data**: the restaurant ticket shows four lines because earlier probe runs added items to the same order. The layout findings don't depend on how many lines there are.
- The dark-mode check flags any surface with luminance > 0.6. Primary buttons (`--primary: #f7f7f4` in dark) were excluded on purpose, after reviewing them in the screenshots.
